# AGENTS.md

Berean is a tradition-aware theology and ecclesiology Q&A system. A user selects a
denomination; that selection determines which documents are treated as authoritative,
and every claim in an answer must resolve to a real, licensed source before it renders.

Internal codename for the retrieval and citation service: **Catena**.

Read this file first. It is deliberately short and points elsewhere.

## Repository

`github.com/ttsu/berean` — a monorepo with **one Go module at the root**. Go ignores the Python
tree, so a second module buys nothing and complicates codegen paths.

- Go module: `github.com/ttsu/berean`
- Gateway binary: `services/gateway/cmd/berean`
- Generated protobuf: `gen/` (gitignored; regenerated by `buf generate`)
- Python package: `services/catena`, managed with uv

## The one-line architecture

**Go is the trust boundary. Python is the model layer.**

Python produces claims; Go adjudicates them. Python's output is untrusted. There is
**exactly one gRPC call from Go into Python per user turn**. If you find yourself adding a
second call per turn, the seam is in the wrong place — stop and raise it.

- `services/gateway` (Go) — auth, sessions, profile resolution, **citation verification**,
  trace persistence, ESV API fetch, SSE to client.
- `services/catena` (Python) — query rewriting, embedding, hybrid retrieval, reranking,
  LangGraph orchestration, generation, ingestion, eval harness.
- `proto/` — the answer object and filter spec. The entire contract between the languages.
  Defined once, generated for both sides. Never hand-maintain a struct on one side.

Detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Decisions and their rejected
alternatives: [docs/adr/](docs/adr/).

## Hard constraints

These are not style preferences. Violating any of them is a correctness or legal failure.

1. **No ESV or NIV text anywhere in this repository.** Not in source, not in fixtures, not
   in test data, and specifically **not in the eval golden set** — that is the likeliest
   place it gets in, because golden sets naturally contain expected passages. Retrieval runs
   on public-domain WEB text; copyrighted translations are fetched at render time via API
   with a deployer-supplied key. See [docs/CORPUS-POLICY.md](docs/CORPUS-POLICY.md).
2. **Corpus IDs are edition-specific.** Write `wcf-1788-american`, never `wcf`. The PCA holds
   the 1788 American revision, which differs from the 1646 original on the civil magistrate.
   A bare work ID is a bug.
3. **Nothing renders unverified.** Every citation resolves to real source text or the answer
   degrades to "I can't source this adequately." Never soften this into a warning.
4. **No token streaming.** Answers cannot stream before verification completes. Stream trace
   events over SSE instead.
5. **Never ship model introspection.** The system explains *provenance* (what was retrieved,
   filtered, checked) and *argument* (the theological case with citations). It never emits the
   model's narrative about its own reasoning. That is post-hoc rationalisation and it is
   corrosive to the entire value proposition.
6. **`docker compose up` must give a working system with no external accounts.** This is the
   acceptance test. If a change breaks it, the change is wrong. No managed-service
   dependencies, no CC-BY-NC models, no proprietary SaaS in the default path.

## Domain vocabulary

Authority tiers are `binding`, `governing`, `advisory`, `contrary`, `excluded`. They are a
stance assigned per corpus, **not** an include/exclude filter — `excluded` means "this
tradition examined and repudiated this," which is a valuable answer a filter cannot produce.

Terms, ID formats, and locator conventions: [docs/GLOSSARY.md](docs/GLOSSARY.md).

## Specs

Specifications are the source of truth and live in [specs/](specs/).

- [specs/SHARED-TECHNICAL-SPEC.md](specs/SHARED-TECHNICAL-SPEC.md) — project-wide
  non-functional requirements. Feature specs may tighten these, never relax them.
- `specs/NNN-<slug>/` — one directory per feature, containing PRODUCT, TECHNICAL, and
  INTEGRATION specs plus a volatile PLAN.

**When you make a decision during implementation that the spec did not anticipate, update the
spec in the same change.** Stale specs are worse than no specs.

## Current phase

Phase 1: ingest one corpus (Westminster Standards, 1788 American revision), naive RAG,
CLI. Goal is to prove citations verify end to end. See
[specs/001-phase-1-pca-baseline/](specs/001-phase-1-pca-baseline/).

Phase 2 (eval harness and golden set) comes **before** Phase 3 (hybrid retrieval and
reranking). This ordering is deliberate and is the thing that separates this project from a
tutorial. Do not reorder it.

## Working agreements

- Read the relevant spec before writing code. If the spec is silent, ask rather than infer.
- Package-level guidance lives in `services/*/AGENTS.md`. The nearest file wins.
- Repeatable workflows are skills in [.agents/skills/](.agents/skills/) — ingesting a corpus,
  adding a tradition profile, running evals.
- Prefer boring, transactional, single-datastore solutions. One Postgres.
- This project is Apache-2.0 and will be open source. Assume downstream commercial use is
  permitted, and pick dependencies accordingly.
